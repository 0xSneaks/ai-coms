## State (evidence)

1. **High — A submitted payment can go uncredited and the UI can ask for another signature.** A single immediate finalized-RPC check follows submission. Pending finality, an intermittent RPC error or a reload leaves the buyer without a durable confirmation path. The UI keeps the signing action available. The server also uses the confirmation request time for the 10-minute cutoff, so a valid payment can arrive within the quote window and still miss credit. Persist the order and submitted signature, disable resubmission while signing or pending, reconcile the same signature across retries and restarts, and enforce the quote window against the transaction's block time. [Client confirmation](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/web/src/App.tsx#L237) · [Pay action](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/web/src/App.tsx#L645) · [Server expiry](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/api/passes.py#L132)
2. **High — Order state and crediting need to be atomic.** Bind the payer at order creation and use that binding for both the client transaction and reconciliation. The current flow gets the payer from the session at confirmation, so a wallet change can strand a valid payment. Order replacement writes cancelled state separately and confirmation ignores it. The entitlement read is outside the sales write transaction. Enforce one active or pending purchase, settle valid in-flight payments and compute the entitlement extension in the same database transaction as the sale. Make duplicate confirms return the original receipt. Prove that a second payment for one order is reconciled or refunded. [Order creation](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/api/passes.py#L91) · [Entitlement calculation](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/api/passes.py#L146) · [Sales transaction](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/api/store.py#L243)
3. **High — Token account checks and rent are incomplete.** The presence check counts any merchant USDC account, while the transaction targets the canonical associated token account. If the destination ATA is absent, the buyer funds its creation, and the app's review screen lists only USDC. A missing buyer ATA cannot fund the transfer. Check the exact source and destination ATAs and spendable USDC, pre-create the merchant ATA before launch, and disclose any SOL cost the buyer can incur. Require the canonical merchant ATA during verification. [RPC lookup](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/api/rpc.py#L48) · [Transaction builder](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/web/src/pay/buildPassTransaction.ts#L47) · [Destination verification](https://github.com/0xSneaks/antigravity/blob/6ae19fcbc09e85ffbace0ecdf154c4055eb224f3/api/verify_pass.py#L154)

The fallback resolver is a stub and the default trusts no proxy geo headers. Nonempty partial or malformed geo can be treated as known. Effective geo coverage, header provenance and a real allowed checkout remain UNKNOWN. Use a trusted deployment geo provider, validate country and subdivision where required, fail closed on incomplete location, and expire sessions with a clear reauthentication path. Confirm the actual listing and in-app restrictions against Cherry policy.
